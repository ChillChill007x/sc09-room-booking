# บทที่ 5 สรุปผล ปัญหา และข้อเสนอแนะ

## 5.1 สรุปผลการดำเนินงาน

ทีมพัฒนาระบบจองห้องอาคาร SC09 เป็นเว็บแอปพลิเคชันที่ใช้งานได้จริงบนคลาวด์ ผลเทียบกับวัตถุประสงค์มีดังนี้

| วัตถุประสงค์ | ผลการดำเนินงาน | สถานะ |
|---|---|:-:|
| 1. ค้นหาและจองห้องโดยไม่จองชนกัน แม้มีคำขอพร้อมกัน | ค้นหาห้องว่างตามเวลา ความจุ อุปกรณ์ ตรวจเวลาชน 2 ชั้น (chain + ล็อกแถว) ทดสอบคำขอพร้อมกัน 5 รายการ สำเร็จ 1 รายการ | ✓ |
| 2. กฎต่างกันตามบทบาท และขั้นตอนอนุมัติที่ตรวจสอบย้อนหลังได้ | Strategy 3 นโยบาย, คิวอนุมัติ, ปฏิเสธต้องมีเหตุผล, เก็บประวัติทุกการเปลี่ยนสถานะ | ✓ |
| 3. แจ้งเตือนอัตโนมัติ | แจ้งเตือนในระบบหลัง commit สำเร็จ ทั้งผู้จองและเจ้าหน้าที่ | ✓ (เฉพาะในระบบ) |
| 4. ออกแบบตาม SOLID และใช้ Design Pattern | ใช้ Strategy, Chain of Responsibility, State, Observer พร้อมวิเคราะห์ SOLID จากโค้ดจริง | ✓ |
| 5. กระบวนการพัฒนาเป็นทีม | 163 commit, 35 Pull Request, branch protection, CI 3 job, deploy อัตโนมัติจาก `develop`, 226 test, line coverage 72.9% | ✓ |

ฟังก์ชันที่ส่งมอบครบตามขอบเขต ได้แก่ CRUD 2 resource หลัก (ห้อง/อุปกรณ์ และการจอง) ความสัมพันธ์ Many-to-Many การค้นหา กรอง เรียง แบ่งหน้า ระบบสิทธิ์ 4 บทบาท Scheduler ตารางการใช้ห้องแบบปฏิทิน แดชบอร์ดสถิติ และคู่มือการใช้งาน

## 5.2 ปัญหาที่พบและแนวทางแก้ไข

| ปัญหา | สาเหตุ | วิธีแก้ |
|---|---|---|
| จองห้องเดียวกันพร้อมกันสำเร็จทั้งคู่ | ตรวจเวลาชนแล้วค่อยบันทึก (check-then-act) 2 transaction อ่านข้อมูลก่อนกันบันทึก | ล็อกแถวผู้ใช้และห้องด้วย `SELECT ... FOR UPDATE` ก่อนตรวจกฎ และเขียน concurrency test ยืนยัน |
| อนุมัติและปฏิเสธพร้อมกันสำเร็จทั้งคู่ | เปลี่ยนสถานะโดยไม่ล็อก | ล็อกแถวการจองแล้วอ่านสถานะล่าสุดก่อนเปลี่ยน Scheduler ตรวจซ้ำหลังล็อก |
| CI ล้มเพราะ Docker Hub rate limit (429) | runner ของ GitHub ใช้ IP ร่วมกัน ดึง base image เกินโควตา | เปลี่ยนไปใช้ AWS ECR Public mirror และให้ job ลองใหม่อัตโนมัติ |
| Flyway checksum ไม่ตรงหลังแก้ไฟล์ migration | มีการแก้ข้อมูลตั้งต้นใน V2 ที่รันบนฐานข้อมูลไปแล้ว | ตกลงกติกาว่าห้ามแก้ migration ที่รันแล้ว ถ้าต้องเปลี่ยนให้สร้างเวอร์ชันใหม่ (V6 ขึ้นไป) |
| Open redirect หลัง login | รับค่า `next` แล้ว redirect โดยไม่ตรวจ | รับเฉพาะ path ภายในที่ขึ้นต้นด้วย `/` และไม่ใช่ `//` |
| รหัสผ่านภาษาไทยยาวทำให้ error 500 | BCrypt รับได้ไม่เกิน 72 ไบต์ แต่ตรวจเป็นจำนวนตัวอักษร | annotation `@MaxUtf8Bytes(72)` ตรวจเป็นจำนวนไบต์ และตอบ 400 |
| ข้อมูลลับเกือบหลุดเข้า repository / แชท | คัดลอกค่าจริงไปวางระหว่างตั้งค่า deploy | เก็บค่าลับใน GitHub Secrets และ environment ของ Render เท่านั้น สร้าง `JWT_SECRET` ใหม่ และใช้ `.env.example` ที่มีแต่ชื่อตัวแปร |
| พื้นที่ดิสก์ของเครื่องพัฒนาเต็ม | cache ของ Maven, npm และ Docker | ย้าย cache และไฟล์ชั่วคราวไปไดรฟ์อื่น |
| งานของสมาชิกชนกันตอน merge | หลายคนแก้ไฟล์กลางเดียวกัน (layout, api client) | แยกเจ้าของไฟล์ชัดเจน merge `develop` เข้า branch ตัวเองบ่อย ๆ และ review ทุก PR |

## 5.3 ข้อจำกัดของระบบ

1. backend บน Render แบบฟรีจะหยุดทำงานเมื่อไม่มีผู้ใช้ระยะหนึ่ง คำขอแรกหลังจากนั้นอาจรอประมาณ 1 นาที
2. แจ้งเตือนมีเฉพาะในระบบ ยังไม่ส่งอีเมลหรือ LINE
3. มี API แก้ไขการจองที่ยังรออนุมัติแล้ว แต่ยังไม่มีหน้าเว็บสำหรับแก้ไข ผู้ใช้ต้องลบแล้วจองใหม่
4. ยังไม่รองรับการจองซ้ำรายสัปดาห์
5. หน้ารายละเอียดการจองไม่อัปเดตเองเมื่อสถานะเปลี่ยนจากแท็บหรือผู้ใช้อื่น ต้องรีเฟรช (backend ป้องกันด้วย 409 แล้ว)
6. `allowed-actions` ตรวจเฉพาะสถานะและเวลา ยังไม่ดูช่วงปิดห้อง ปุ่มอาจแสดงแต่กดแล้วได้ข้อความแจ้งว่าห้องปิด
7. ยังไม่มี test อัตโนมัติฝั่ง frontend และ coverage ของ controller กับ security ยังต่ำ (21.4% และ 20.3%)
8. ข้อมูลความจุและอุปกรณ์ของห้องเป็นข้อมูลที่ทีมรวบรวมเอง อาจไม่ตรงกับสภาพจริงทั้งหมด

## 5.4 ข้อเสนอแนะและแนวทางพัฒนาต่อ

1. **แจ้งเตือนผ่านอีเมลหรือ LINE** — เพิ่ม class ที่ implement `NotificationSender` โดยไม่ต้องแก้โค้ดเดิม (ได้ประโยชน์จาก Observer + OCP)
2. **การจองซ้ำรายสัปดาห์** — สร้างการจองหลายรายการจากรูปแบบเดียว ส่งผ่าน chain ตรวจกฎทีละรายการภายใน transaction เดียว
3. **หน้าแก้ไขการจองและปุ่ม "จองอีกครั้ง"** — ใช้ API `PUT /bookings/{id}` ที่มีอยู่แล้ว
4. **อัปเดตสถานะแบบ real-time** — ใช้ Server-Sent Events หรือ WebSocket หรือดึงข้อมูลใหม่เมื่อกลับมาที่แท็บ เพื่อแก้ข้อจำกัดข้อ 5
5. **ให้ `allowed-actions` ตรวจช่วงปิดห้อง** — เรียก `RoomQueryService.isClosed()` ก่อนคืนรายการ action
6. **เพิ่ม test** — controller ที่ยังไม่มี test (5 จาก 11), security filter, และ test ฝั่ง frontend (React Testing Library / Playwright)
7. **ปรับปรุงตาม SOLID** — แยก `BookingLifecycleServiceImpl` ให้เล็กลง, เปลี่ยน `switch` ของ `BookingAction` เป็น map ของ handler, แยก `BookingRepository` ตามหน้าที่ (รายละเอียดใน [solid-analysis.md](../solid-analysis.md))
8. **QR Code สำหรับ check-in หน้าห้อง** — ยืนยันว่ามาใช้ห้องจริง ลดการ check-in จากที่อื่น
9. **รายงานสถิติเพิ่มเติม** — ช่วงเวลาที่ใช้มากที่สุด อัตราการไม่มาใช้ห้องรายบุคคล และส่งออกเป็น CSV

## 5.5 สิ่งที่ได้เรียนรู้

- การแยกกฎเป็น Strategy และ Chain ทำให้สมาชิกแต่ละคนพัฒนาและทดสอบส่วนของตัวเองได้อิสระ และเพิ่มกฎใหม่ได้โดยไม่แก้ของเดิม
- test ที่ผ่านครบไม่ได้แปลว่าไม่มีบั๊ก บั๊กสำคัญที่สุด (การจองพร้อมกัน) พบจากการทดสอบบนเว็บจริงและต้องเขียน concurrency test เพิ่ม
- การ inject `Clock` ทำให้ทดสอบกฎที่ขึ้นกับเวลาได้แน่นอน
- CI, branch protection และ code review ช่วยจับข้อผิดพลาดก่อนเข้าสู่ `develop` และทำให้ deploy ได้บ่อยอย่างมั่นใจ
- ข้อมูลลับต้องแยกออกจากโค้ดตั้งแต่ต้น และ migration ที่รันแล้วต้องถือว่าแก้ไม่ได้
